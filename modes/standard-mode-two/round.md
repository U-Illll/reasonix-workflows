# Skill: mode-two-round（标准模式二 · 协作规则与状态机）

> 定义"一轮 round 怎么跑、什么时候停、出故障怎么办"。由 `Standard_Mode_Two` 框架 skill 在每个 round 的 T0 选型与 T6 终止判定时加载。
> 单一事实源：状态机、五轴、回执五关、探索树协议、终止条件、回执纪律只在本模块定义。

---

## 1. round / turn / budget（2.4）

- **round**：一轮完整 T0-T6（任务书下发 → 回执 → 讨论 → 裁决 → 落盘）。round_id 全局递增，写入任务书与回执，是讨论层锚定数据的唯一凭证。
- **turn**：执行层单次工具调用。一个 round 内可有多个 turn（执行层内部自行串行推进）。
- **budget**：每 round token 预算——执行层 80 turn、讨论层 2 次 subagent、指挥官 1 次裁决。预算耗尽 = 软退出触发条件之一（§8）。

## 2. round 状态机（13.1，LangGraph round_engine.py 的语义说明书）

每个 round 从下发到判定经历六个状态，指挥官在 T6 判定后驱动状态迁移：

```
IDLE(空闲) → DISPATCH(已下发) → EXECUTING(执行中) → RETURNED(已回执)
           → DISCUSSING(讨论中) → ADJUDICATED(已裁决) → IDLE(下一轮)
                                    ↘ TERMINATED(终止,写终局报告)
                                    ↘ BASE_SWITCH(换基底,重置计数)
```

**每个状态的进入条件与超时**：
| 状态 | 进入条件 | 超时/异常 |
|---|---|---|
| DISPATCH | 任务书写完且通过自检（五要素齐：目标/已知/死步骤/约束/回执格式） | - |
| EXECUTING | 执行层确认接收 | 浏览器域 timeoutSec≥900；超时仍 running 用 agent_state 查存活（nSteps 不动 ≠ 卡死）；Windows 域 hook 挂起为正常态，watchdog 周期性探活 |
| RETURNED | 回执通过 schema 校验（round_id 匹配、status 合法、data 长度合规） | 校验失败 = 回执漂移 → §3 故障处置 |
| DISCUSSING | parallel_tasks 双顾问回收完成，或单顾问超时（5 分钟）后强制回收已有结果 | 超时强制回收 |
| ADJUDICATED | 指挥官裁决落盘（记忆摘要写入 S1） | **没有落盘的 round 等于没发生** |

**多 round 依赖管理（13.3）**：
- 链式依赖（默认）：round N+1 任务书依赖 round N 回执 → 必须串行。
- 分叉依赖：一个 round 产生两个互不依赖的待验证点，若活状态隔离（不同域/不同实例）可同时进入两个 EXECUTING；同域内仍串行。
- 冻结依赖：C2 分治爆破中已成功的策略进入冻结态，后续任务书自动带"沿用 frozen 策略，不重新验证"约束。
- 指挥官在 ADJUDICATED 时同步更新依赖表（dependency ledger）：`round_N 产出 → 消费于 round_M`。此表是换基底与终局复盘的第一手依据。

## 3. 故障场景与处置表（13.2）

| 故障 | 症状 | 处置 |
|---|---|---|
| 执行层超时 | EXECUTING 超阈值，agent_state 仍 running | 续等；nSteps 持续增长=健康；超 2 倍阈值 → 截停（agent_stop）再派 |
| 执行层断连 | Firefox 关闭 / MCP 失联 / hook attach 丢失 | 进入 T3 人工介入：请用户重启浏览器或目标进程，恢复后回执带 reconnect 标记 |
| 回执漂移 | round_id 对不上 / status 非法 / data 超长 | 丢弃该回执，记 S1"执行层格式漂移"踩坑，重派同 round（计数不重置） |
| 讨论层空转 | B/C 回收内容与数据无关（跑题） | 指挥官直接丢弃，附 30 字摘要重派一次；仍跑题 → 本轮单顾问模式（C3 降级） |
| 状态串味 | 并发操作同一 tab/hook，回执数据错乱 | 立即 stop 所有执行层，回滚到最近 ADJUDICATED，按 P1 串行重派 |
| 记忆写失败 | remember 落盘失败 | 降级写档案文件（S2），下轮开始前补写；绝不带"未落盘的裁决"进入下一轮 |

## 4. 任务书协议（4.5，下行）

**格式**（≤1500 字，模板见 templates/task-brief.md）：

```
Round: <N> | Domain: <browser|windows|static|explore>
目标: <一句话,含成功判据>
已知: <关键事实,含反证>
第1步: <工具名> <参数> <目的>
第2步: ...
只做这N步,不绕圈。用 <指定工具> 返回值汇报,不写文件。
约束: <安全/成本/风控约束>
回执格式: {round_id, domain, status, data, confidence}
```

**自检**（附录 T.1 提炼）：目标是否可判定？已知是否漏掉上轮关键反证？死步骤是否只指向唯一方向？回执格式是否明确？
**反例会漂移**："探索一下 signFn 的算法"——太开放，worker 会自己发明路线。**正例**：2026-07-31 flash 模型 任务书，显式函数签名 + "静态密钥/IV 为何不可用" + 四步各带工具名和抓取目标。

**skill 引用（2026-08-13 实测）**：D3（Codex/Claude Code）的高频任务书可固化为 skill，任务书「死步骤」节直接引 skill 名替代现写规范——样板 `reasonix-worker-brief` 已双端落盘（codex `~/.cache/codex/skills/`、claude `~/.cache/claude/skills/`）。派发格式：「按 reasonix-worker-brief 执行：<目标/死步骤/约束>」。实测：claude -p 无头下内置 Task*/Skill 默认可用，`--allowedTools` 白名单只约束 MCP 工具、不影响内置 Task*。

## 5. 回执协议与纪律（4.5 + 附录 P，上行）

**Schema**（五字段必带，完整 JSON 见 templates/receipt-schema.json）：

```json
{
  "round_id": 7, "domain": "browser",
  "status": "partial_success | failed | dead_end | success",
  "data": "<砍量后的原始数据,≤3000字>",
  "confidence": 0.8,
  "drift_hint": "<finishReason / likelyDrift 核查结果>",
  "node_id": "<探索节点锚；E 相位/探索类回执必带>",
  "side_effects": ["<副作用声明：写文件/发请求/hook 安装…；空数组=无副作用>"],
  "vault_refs": ["<引用的 vault 句柄；阶段 B 起启用>"]
}
```

（后三字段为 v1.1 扩展：node_id 探索类必带；side_effects 所有执行回执必带——声明义务现在生效，幂等表机制见阶段 B；vault_refs 阶段 B 起启用。）

**协议铁律**：①回执必带 round_id（讨论层锚定，杜绝张冠李戴）；②status=dead_end 是合法状态不是失败（触发换基底，进软退出计数）；③data 必须砍量，海量原始数据走降载通道。

**回执五关（T3 收件时，P.2 + v1.1 升级）**：
1. schema 关：五字段齐全且类型正确；探索类回执带 node_id，含副作用动作必带 side_effects（空数组=无），句柄引用带 vault_refs。
2. 数据纯度关：data 是否混入推断句（含"我认为/可能/应该"）？有则退回重写或标注"含推断，讨论层注意甄别"。
3. 锚定关：data 是否对得上任务书要求抓取的目标？对不上 → 漂移，核查 driftHint。
4. 净化解（v1.1 新增）：敏感扫描——密钥模式（sk- 前缀/Bearer/长 base64 段）、凭据特征、订阅/代理类明细；命中即阻断（该回执不进讨论层，就地净化或退回），并记入观测日志。
5. 漂移关（v1.1 新增）：规则检测——U+FF5C 类全角变体、DSML 残留、think 标签泄漏、JSON 非法、异常转义序列。命中 → 按 §3 回执漂移处置；同时记入漂移率观测。

**漂移/净化规则检测（观测模式，阶段 A 起）**：五关第 4/5 关的规则性部分由 `Standard_Mode_Two/scripts/drift_scan.py` 执行（输入回执文本，输出命中类别与计数）；观测模式=只记不拦（净化解的敏感命中除外——它是硬线，一律阻断）：漂移率、净化命中数逐轮记录，积累 2 周真实基线后（阶段 C）再决定是否升级自动拦截阈值。

**降载通道（P.3）**：data 超 3000 字先落盘，回执只留路径+摘要（`artifact_path=/archive/<战例>/roundN_xxx.json`）；指挥官取回 artifact → 由 D4 静态 fleet 并行分析 → 分析结论再进讨论层。**这条纪律是"上下文爆炸"防线的最前线**。

## 6. 五轴分支速判（第六部分，每轮 T0 执行；v1.1 四轴→五轴）

五轴可嵌套。每轮循环开始时对照下表选型，写进任务书头部（如 `Mode: R2+C1+P3+T1+X1`）：

```
1. 任务性质? → 轴1(R1/R2/R3/R4)
2. 循环策略? → 轴2(C1 默认,除非信号命中 C2/C3/C4)
3. 并行度?   → 轴3(P3 默认;执行层并行看活状态隔离;P5 见轴5)
4. 成本档?   → 轴4(T1 默认;可疑→T4;风控→T3)
5. 探索广度? → 轴5(X0 单线默认; X1 单节点多候选; X2 树形探索)
```

**轴1 任务性质**：R1 浏览器攻坚（网页侧混淆/签名/加密请求）→ D1+D4；R2 本地二进制攻坚（进程内密钥/数据库加密/需 attach）→ D2+D3；R3 混合攻坚（链路跨端）→ D1+D2+D3 按依赖排先后；R4 纯静态分析（仅离线）→ D4 fleet + Ghidra + codegraph/serena。**R2 前置条件**：低价值测试号、只读 hook、不碰登录/网络/写内存；风控评估未过 → 转 R4 有限推进。

**轴2 循环控制**：C1 三角质疑（默认：B/C 并行挑刺 → A 裁决）；C2 分治爆破（目标天然分块：A 拆两块，B/C 各领一块出清单 → 合并下发 → 结果对冲，冻结成功策略逐块收敛）；C3 单刀直入（指挥官有明确经验的单步或最后一击：跳过 B/C 直接 agent_call_tool 直驱，省 token 高风险）；C4 取证升格（强分歧/软退出命中/跨域验算三条之一 → 派 D3 取证，结构化结论作第 4 输入）。

**轴3 并行度**：P1 单域串行（默认，依赖链强/共享活状态）；P2 双域并行（两域无依赖，活状态分域隔离）；P3 讨论并行（每轮默认，B/C 同时挑刺）；P4 静态 fleet 并行（≥3 个本地文件需独立分析）；**P5 节点级 fleet 并行（v1.1 新增）**——四条件全满足才允许：①死状态（无共享活会话）②只读（工具面白名单化）③证据锚定（产出带可复现证据）④出口组合可用（每节点绑定独立出口组合：IP 出口+账号，不得复用）。**并行铁律**：讨论层并行永远安全（只读）；执行层并行只在"活状态隔离"时允许；同一 tab / 同一 hook 会话内并行一律禁止；探索并行度 ≤ 可用出口组合数（宁可少方向，不挤同一出口）。

**轴4 成本信任**：T1 flash 档探路（默认，deepseek-v4-flash/flash 档模型/glm）；T2 强模型直驱（有明确经验的单步/最后一击，agent_call_tool，≤2 次/战例）；T3 人工介入（风控/封号/反爬跳转/终止失效/配 key → 挂起循环人工拍板）；T4 信任降级（连续 2 轮执行层结论可疑：driftHint 显示纯文字无工具、或 data 与 round_id 对不上 → 换 worker 档位；降级后仍可疑 → T3）。

**轴5 探索广度（v1.1 新增）**：X0 单线（默认=现状，一个目标一条路线）；X1 单节点多候选（一个目标多个假设并行验证，各候选独立回执）；X2 树形探索（多节点并行 + 探索卡存档 + 节点树分支管理，即 §6.5 探索树协议启用）。判定信号：任务形态含"探索面不明/多候选路径/需要广度枚举" → X1/X2；目标明确只是难 → X0。X1/X2 派发时按 §6.5 准入条件执行。

**T4 关键依据**：assist 模式下"纯文字无工具"会被强制成 final，真结论与模型漂移经 getState 分不开，必须看 driftHint + runlog 的 finishReason 才能区分——这是信任降级的证据基础。

## 6.5 探索树协议（E 相位专用，v1.1）

E 相位（探索/发散）与 C 相位（收敛/深挖，即 T0-T6）的切换与详述见框架 skill「探-收双相位模型」节。本节只定协议对象。

**探索卡（节点压缩存档，模板 `Standard_Mode_Two/templates/explore-card.md`）**：
- **双段式**（A 只写第二段，省 A 的 token 又保质量）：①结构化事实段（≤500 字硬限）由探索 agent 写——`node_id / parent / 假设 / 已试动作 / 结果（成功|死路|不确定） / 证据指针 / 候选子女方向`；②裁决摘要（≤100 字）由 A 写。
- **压缩时机**：节点终止时一次性写卡；长节点加里程碑即时写（防中途崩丢）。
- **死路卡三件套**（最高价值产出）：结论 + 死因 + 证据指针——过程上下文丢弃，防跨轮重踩。
- **继承边界**：子节点只继承「探索地图 + 父卡摘要 + 公共已知」，不继承父的完整过程（防膨胀与污染传导）。
- **跨轮回填**：E0 探索地图只引「卡索引 + 摘要行」（S1.5 档案），防历史积累淹没。

**节点树 ledger（JSONL 单调追加）**：`node_id, parent, status, card_path, ts`（脚本：`scripts/explore_ledger.py`）；根=探索地图；**旧节点只读**（分支回退不重放，阶段 C 启用 .bN 分支语义；阶段 A/B 先以只读纪律落地）。

**预算与终止**：单节点 max_steps + 输出上限（探索卡 ≤500 字）；深度 ≤2-3 层 + 节点预算 + 收益递减即停（E4 判定）。

**准入条件（全部满足才可派发探索节点）**：只读边界 + 死状态 + 证据锚定 + 出口组合可用（`exit_ref` 登记于节点卡）——与 P5 同条件；出口分配见 `scripts/exit_pool.py`。

## 7. 三级终止条件（第八部分，循环的强制出口）

| 级别 | 条件 | 判定方 | 动作 |
|---|---|---|---|
| 硬退出（成功） | 成功判据达成：明文函数捕获 / <KEY> 提取且解密脚本跑通 / 参数契约还原 | 指挥官 | 写终局报告 → 归档 S2 → 结束 |
| 硬退出（不可行） | 高置信度证明"该方向物理不可行"（如"服务端根本不校验签名"） | 指挥官 | 记录死路证明 → 归档 → 结束 |
| 软退出（死胡同） | 连续 3 轮回执报错完全一致（比对 S1 记录） | 指挥官 | 换基底策略；换后仍 3 轮一致 → 人工 |
| 软退出（预算） | round budget 耗尽（80 turn 或 6 轮无进展） | 指挥官 | 收敛为"阶段性结论"落盘，暂停 |
| 人工中断 | 反爬跳转 / 风控信号 / 用户介入 / 终止失效 | 用户 | 挂起循环，恢复或放弃 |

**软退出"一致报错"判定（8.2 + 18.2 伪代码）**：比对最近 3 轮回执的 status 与报错文本——完全相同 → 死胡同；有变化但无进展 → 检查是否"策略内收敛"（换工具组合在缩小搜索空间），是则继续；变化且方向翻转 → 正常探索继续。**关键区分**：drift / idle-timeout 的 finishReason ≠ 路线走不通。判定前必须核查 driftHint——"模型懒得调工具"和"工具确实没命中"是两回事，前者走 T4 信任降级，后者才进软退出计数（drift 回执不计入"一致报错"）。

**换基底候选池（8.3）**：

| 当前基底 | 可换去向 |
|---|---|
| 浏览器域动态（hook 全绕过） | 静态域（Ghidra 反编译沙箱 JS）+ 沙箱替换（自实现 AES 复算） |
| Windows 域 Frida hook（无命中） | 内存扫描（魔术 <MAGIC>）+ key_blob 静态逆向 + 登录钩子（备选登录钩子） |
| 直驱强模型（烧钱无果） | 降回 flash 档 + 分治爆破（缩小变量） |
| 单一战例 | 跨战例同构迁移（WEB-SIGN 沙箱绕过经验 → 桌面目标 Frida 选点） |

**终止判定伪代码（18.2 核心）**：

```
def check_termination(decision):
    if decision.success_criterion_met: return TERMINATED   # 硬退出-成功
    if decision.infeasible_proven:     return TERMINATED   # 硬退出-不可行
    if identical_error_3_rounds():     return BASE_SWITCH  # 软退出-死胡同
    if budget_exhausted(80 turns or 6 rounds_no_progress):
                                        return BASE_SWITCH # 软退出-预算
    if human_interrupt_flag:           return TERMINATED   # 人工中断
    return CONTINUE
```

## 8. S1 记忆检索与写入（5.2 + 16.1）

**记忆格式（S1，每条按模板落盘）**：
```
标题: <domain>-<战例>-<要点>   例: desktop-keyblob-180B结构已确认
正文: 结论(一句话) + 证据链(工具名+回执round_id) + 反证(若适用) + 下一步候选
标签: [desktop|web|flash 模型|browser|windows|static] + [踩坑|反证|成功|死路|决策]
```

**分域机制**：按 domain tag 分域存储与检索；浏览器域踩坑与 Windows 域踩坑互不污染，但检索支持跨域模糊匹配（"沙箱绕过 hook"这类经验两域同构）。

**写入时机（强制）**：①每 round 结束：踩坑/反证/成功摘要（≤100 字），失败也要写（负结果值钱，防重复踩）；②换基底时：写明"死路证明"（什么被排除、为什么）；③战例终局：终局报告写 S2 档案，S1 只留索引指针。

**检索流程（裁决前必做，16.1）**：
```
1. 构造 query: 本轮待裁决问题的核心名词 + domain tag（如 "IV 运行时变换" + browser）
2. 检索 top-5，按相关度排序；优先展示"反证/死路"类
3. 逐一核对: 命中的踩坑是否已排除当前候选方向？命中的成功策略是否可复用？
4. 0 命中: 显式记录"空检索"（防下次重复查），判定"这是全新探索"
5. 裁决引用: 命中的记忆标题写进裁决模板的"S1 检索命中"节
```

**容量纪律（5.5）**：每轮裁决只检索 top-5；超过 5 条优先"反证/死路"类（最省试错成本）。落盘协作遵循 `memory-codegraph-collab` 的 remember 三步与链式复核。

## 9. 指挥官自查清单（附录 T，连续 2 轮 CONTINUE 但收敛感不明显时）

- **任务书质量**：目标可判定吗？已知漏了上轮关键反证吗？死步骤只指向唯一方向吗？回执格式明确吗？
- **讨论质量**：B/C 本轮给**新**方向了吗（两轮雷同 = 前情提要失效或数据没换）？我只是重述 B/C 观点吗（裁决必须有增量：引用记忆/排除项/跨域经验）？出现回声室了吗（B/C 都在附和我 → 临时调换 B/C 视角）？
- **方向质量**：本轮方向与前三轮实质不同吗（换汤不换药 = 软退出信号）？还有未试的基底策略吗（对照 §7 候选池）？现在停止能写出"阶段性结论"吗（写不出 = 任务书有问题）？
- **资源**：预算剩余 <20% 且无突破信号 → 直接转软退出；执行层有 drift 迹象未处理（recentToolCalls 停滞 = 纯文字化）→ 先 T4 再谈方向。

## 10. 多战例并发管理（附录 R）

**允许并发的条件**：活状态隔离（不同域/不同浏览器实例）；讨论层天然可并行（每战例自己的 B/C 对）；**指挥官单线程铁律**——同一时间只裁决一个战例的 round，另一战例的 round 进入等待队列（S1 检索与裁决上下文每切换一次都有污染风险）。

**资源分配**：执行层实例每战例独立；S1 记忆按 domain tag + 战例名过滤；token 预算每战例独立核算；档案目录每战例独立。

**裁决优先级**：①人工中断挂起中的战例优先恢复（用户等待成本最高）→ ②已有 C4 取证升格等待结果的优先（执行体已烧钱）→ ③剩余预算越少越优先 → ④FIFO。

## 11. 成本与预算（附录 M）

**单轮成本构成（浏览器域基准）**：执行层（flash 档，≤80 turn）= 主成本；讨论层 B/C（2 次只读 subagent）+ 裁决（1 次）= 小；记忆落盘/检索 ≈ 0；取证升格 C4（Codex/Claude 付费端点）= 高，每 3 轮 ≤1 次。

**预算规则**：round 级 80 turn / 2 subagent / 1 裁决；战例级 6 轮无实质进展触发预算软退出，总轮数 ≤12（超限强制人工评审）；档位级 T1 占 80% 轮次、T2 只留最后一击（≤2 次/战例）；数据级 >3000 字先落盘，砍量优先免费 worker（复用平台模式①'）。

**成本异常信号**：连续 3 轮 C4 升格（预算失控 → 检查"执行体隐性参与讨论"）；单轮 token 超基准 2 倍（任务书太开放）；讨论层占比 >40%（B/C 重复批评 → 前情提要失效，考虑 C3 降级）。

## 12. LangGraph round 状态机引擎（scripts/round_engine.py）

**用途**：把 §2 的 round 状态机做成可持久化、可恢复、可核对的工具。它是 L4 的**辅助记录器/校验器**，不是循环主控（框架 skill §3 定案）。

**驱动方式**（主 Agent 通过 bash 调用，venv 见 scripts/README.md）：
```bash
# 登记一个 round 的状态迁移（由指挥官在 T0/T1/T3/T4/T5/T6 各阶段调用）
python round_engine.py transition --campaign campaign-desktop --round 5 --to EXECUTING --thread-id <id>
# 查询当前状态与历史
python round_engine.py status --campaign campaign-desktop --round 5
# 终止判定辅助（传入最近 3 轮回执，输出建议；最终判定权仍在指挥官）
python round_engine.py check-termination --campaign campaign-desktop --receipts receipts.json
# 中断后恢复（拿到上次 ADJUDICATED 状态继续）
python round_engine.py get-state --campaign campaign-desktop --round 5
```

**职责边界（红线）**：状态机只做状态跟踪/超时判定/故障分支建议/持久化/多战例隔离（thread_id）；**不**代替指挥官写任务书、**不**调用执行层、**不**裁决。它在无 LangGraph 依赖时可退化为纯标准库实现（round_engine_min.py），接口一致。
